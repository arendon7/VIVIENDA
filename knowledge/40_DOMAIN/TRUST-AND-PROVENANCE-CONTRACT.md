# VIVIENDA — Trust and Provenance Contract V0.1

Date: 2026-08-25
Status: Cross-product contract

## Objective

Make every consequential financial/legal output explainable, source-aware and visually honest.

Trust in VIVIENDA should not depend on users accepting a black box. It should come from knowing:

- where a number came from;
- when it was valid;
- what assumptions were used;
- what VIVIENDA calculated;
- what a third party must still decide;
- what the user can correct.

## Canonical output types

Every material value/output must map to one canonical type.

### USER_DECLARED

Entered directly by user.

Example:

- monthly household income;
- approximate current payment.

UI label when useful:

> “Dato que ingresaste”

### DOCUMENT_EXTRACTED

Extracted from user-provided statement/contract/document.

Metadata:

- file/document ID;
- page/region where possible;
- extraction confidence;
- user-confirmed status.

UI:

> “Extraído de tu extracto”

If confidence is low, force confirmation before consequential calculation.

### PUBLIC_REFERENCE

Current/public information from lender, regulator or other validated source.

Examples:

- public reference rate;
- current program condition;
- UVR value;
- bank procedure.

Required metadata:

- source organization;
- source URL/reference;
- effective date if available;
- last verified date;
- target segment/conditions.

UI:

> “Referencia pública”

Never label as personalized offer.

### PARTNER_DATA

Data supplied through validated commercial/technical partner relationship.

Required:

- partner;
- timestamp;
- scope;
- whether binding/non-binding;
- user/transaction match.

### CALCULATED

Deterministic result derived from known inputs under a versioned formula.

Required:

- method ID/version;
- input references;
- rounding policy;
- calculation timestamp.

Examples:

- monthly equivalent rate;
- baseline amortization output;
- payment burden ratio.

### ESTIMATE

Result that includes missing/approximated inputs or simplified model.

UI must surface uncertainty.

Example:

> “Estimación — falta confirmar tu tasa.”

### SIMULATION

Counterfactual result under explicit assumptions.

Examples:

- pay COP 300k more monthly;
- transfer at hypothetical rate;
- UVR path under assumed inflation.

A simulation is not a prediction.

### PLATFORM_RECOMMENDATION

VIVIENDA ranks or recommends an action based on a defined decision model.

Must include:

- primary reason;
- important tradeoff;
- model/version;
- whether compensation/partner relationship can exist.

A recommendation is not bank approval or legal representation.

### THIRD_PARTY_OFFER

Actual offer/quote generated by a bank/partner.

Must preserve:

- issuer;
- validity period;
- conditions;
- version/date;
- binding status.

Do not modify headline economic terms in presentation.

### THIRD_PARTY_DECISION

Approval, denial or official status from bank/authority/other external actor.

VIVIENDA may explain it but must not represent itself as issuer.

### AUTOMATED_LEGAL_SCREENING

Rule-based/AI-assisted preliminary classification.

UI:

> “Revisión preliminar”

Must state when professional verification is recommended/required.

### PROFESSIONAL_LEGAL_CONCLUSION

Conclusion produced within a direct professional relationship after appropriate legal review.

Must be attributable to professional/case context and not visually collapse into ordinary automated product output.

## Provenance record

Suggested canonical shape:

```text
provenance_id
value_or_output_id
type
source_name
source_reference
source_url
source_effective_date
source_retrieved_at
input_ids[]
method_id
method_version
confidence
user_confirmed
reviewer_verified
expires_at
notes
```

Not every field is required for every type, but consequential values need enough information to be auditable.

## Freshness classes

### STATIC

Principle/fact unlikely to change frequently.

Still record source version/date where regulatory.

### PERIODIC

Changes on known cadence.

Examples:

- published bank rate tables;
- UVR value;
- program conditions.

### VOLATILE

May change quickly or is user-specific.

Examples:

- personalized quote;
- current loan balance;
- lender approval state.

### EVENT_BOUND

Valid only in a period/window.

Examples:

- annual restructuring window;
- offer expiration;
- procedural response deadline.

UI should reflect freshness materially when it changes decision quality.

## Signature UI component — Source/Freshness

Compact default pattern:

> **Referencia pública · FNA · Actualizada 21 ago 2026**

Expandable detail:

- exact source;
- applicable conditions;
- last check;
- link/reference;
- disclaimer about personalized decision.

For user/document data:

> **Tu extracto · corte 15 ago 2026 · confirmado por ti**

## Signature UI component — Output Type

Use small language cues, not a rainbow of badges.

Examples:

- Estimación
- Simulación
- Oferta de Banco X
- Revisión preliminar
- Verificado con tu extracto

Badge alone is insufficient; consequential distinction must also appear in copy.

## Recommendation explanation

Every “best option” recommendation must support:

### Why this appears

At minimum:

- main criterion;
- secondary criterion;
- relevant constraint;
- major tradeoff.

Example:

> “Aparece primero porque, con tus supuestos, reduce el costo total frente a mantener tu crédito y conserva una cuota dentro del rango que definiste. Requiere asumir gastos de traslado.”

### Ranking methodology

User should be able to access:

- ranking factors;
- partner/commercial policy;
- freshness;
- whether all market alternatives are covered.

Never imply “whole market” unless coverage supports it.

## Commercial conflict disclosure

If VIVIENDA receives compensation from a financial/insurance/other provider:

- disclose the category of compensation;
- disclose whether it affects ranking;
- ranking engine must not silently optimize for commission unless explicitly framed as sponsored placement and separated from recommendation.

Sponsored placements, if ever used, must be visibly distinct.

## DIY disclosure

For an opportunity users can safely execute directly:

Show:

> **Puedes hacerlo directamente con tu entidad**

Then:

- verified channel;
- what to request;
- what evidence to retain;
- last verified date.

Assisted option can coexist without visually sabotaging DIY.

## Uncertainty language

### High confidence

> “Con las condiciones confirmadas de tu crédito, el modelo calcula…”

### Medium

> “Con los datos de tu extracto y estas suposiciones, estimamos…”

### Low

> “Esta es una aproximación inicial. Para calcularlo con precisión necesitamos…”

Avoid vague “puede variar” as the only explanation.

## User corrections

When extracted or inferred data affects a result:

- user can see it;
- user can correct it;
- recalculation occurs transparently;
- previous source value can remain in audit history where appropriate.

Do not silently overwrite official document value with user value; preserve provenance of both and mark which one drives current scenario.

## AI disclosure policy

Do not advertise “AI” on every automated action.

Disclose AI where it matters to trust or user rights, especially:

- document extraction;
- classification;
- generated explanations;
- recommendations where model involvement is material.

The user should know what can be wrong and how to correct/escalate it.

## Privacy-purpose pattern

Before a sensitive upload:

### What we need

> “Tu último extracto del crédito.”

### Why

> “Para confirmar saldo, tasa, seguros y plazo y dejar de usar aproximaciones.”

### What we do not need

Where feasible:

> “No necesitamos tu clave bancaria.”

### Control

Explain retention/deletion and whether document is shared with any third party.

## Error handling as trust

Never turn system uncertainty into user blame.

Examples:

Bad:

> “Documento inválido.”

Better:

> “No logramos identificar la tasa en este archivo. Puedes indicarla manualmente o subir otro extracto.”

Show what part succeeded.

## Legal basis citations in product

Main task flow should use plain language.

Detailed source drawer can show:

- law/article;
- regulator guidance;
- last review date;
- professional notes where appropriate.

Avoid dropping long statutory text into result screens.

## Analytics/privacy boundary

Generic analytics should receive event/state identifiers, not raw sensitive values by default.

Examples acceptable conceptually:

- `calculation_completed = true`
- `confidence_class = C1`
- `upload_failed_reason = unsupported_format`

Avoid without explicit architecture:

- exact balance;
- income;
- identity;
- statement contents;
- legal case details.

## Trust acceptance criteria

For any consequential result, a user should be able to answer:

1. Where did this number/information come from?
2. How current is it?
3. What did VIVIENDA calculate?
4. What assumption could materially change it?
5. Is it an estimate, simulation, recommendation or real offer/decision?
6. Can I correct the underlying data?
7. Who makes the final external decision?
8. Does VIVIENDA get paid if I choose this option?

Not every answer must be visible at once, but all must be discoverable without contacting support.
